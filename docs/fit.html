How the memory is worked out

The method comes from the LLM Inference Calculator by Alex Ziskind (MIT license, copyright 2025 Alex Ziskind). We re-implemented its rule in JavaScript, with the context length fixed at each model's maximum and single-user, token-by-token (incremental) decoding:

Memory = (weights + KV cache) × 1.1. The 1.1 is the calculator's 10% allowance for fragmentation and buffers. Weights are the real file size of the build we measured (the calculator uses parameters × bytes per parameter instead). The KV cache is the memory that grows with context; its choices (F16, Q8, Q4) use the calculator's factors, and Q4 is its default.

Two KV estimates. Calculator rule is the calculator's own: weights × 0.2 × (context ÷ 2,048) × K, with K = 2 (F16), 1 (Q8) or 0.5 (Q4). It grows linearly with context and ties the cache to the weights' size, so at 262,144 tokens it gives far more memory than real models use (over 1,500 GB of cache for a 119 GB model). Typical, the default, is LLMeter's own rough rule instead: a typical 30B model's F16 cache is 256 KB per token (64 layers × 8 KV heads × 128 dims × 2 × 2 bytes), scaled by the square root of the model's active size (total size when active is unknown). Real caches vary a lot with the architecture (compact attention such as MLA or hybrid layers uses far less), so treat it as an estimate, not a measurement.

Fits means the total is within 90% of the machine's memory (the system keeps the rest). A cluster adds the memory of its machines. Speed is measured or estimated as on the Rack page: a number from a published run when we have one; otherwise, for dense models, the measured Qwen3.8 27B speed on the same machine scaled by file size (striped bar, “est.”). Mixture-of-experts models with no published run get no estimate. Context lengths marked “assumed” have no figure in our data (262,144 is used).
